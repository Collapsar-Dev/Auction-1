# ADR-001. Стек и отклонения от PRD в версии 0.1

Статус: принято · 2 нояб. 2026

## Стек

| Часть | PRD 7.1 | Версия 0.1 | Почему |
|---|---|---|---|
| Сайт | Next.js, TypeScript | Next.js 15 (app router), клиентские страницы, три языка | как в PRD |
| Сервер | NestJS, REST + WebSocket | NestJS 10, REST | WebSocket заменён опросом (см. ниже) |
| База | PostgreSQL 16 | PostgreSQL 16, SQL-миграции без ORM | меньше зависимостей, полный контроль над блокировками строк |
| Очереди и таймеры | Redis + BullMQ | цикл-сторож в процессе API (`SchedulerService`, раз в 2 с) | один процесс проще поднять и тестировать; все задачи идемпотентны (блокировки строк, dedupe-ключи уведомлений), поэтому перенос в BullMQ не меняет логику |
| Файлы | S3 | локальная папка `apps/api/storage`; закрытые файлы — только по подписанной ссылке на 5 минут | интерфейс `Storage` такой же, как будет у S3 |
| Ключи | KMS | `FakeKms`: AES-256-GCM мастер-ключом из окружения + политика «не раньше closes_at» | см. 7.4 |
| Шлюз, KYC, SMS, email | фейковые адаптеры | `FakeGateway` (+ страница-песочница банка, состояние в `storage/fake-gateway.json`), `FakeKyc` (+ песочница), `FakeSms`, `FakeEmail` (адреса с `+fail` имитируют ошибку) | P-1 |

`lots.auction_type = 'type1'`. Правила типа 1 собраны в модулях `bids`, `reveal`, `lots/eligibility`; новый тип добавляется новым значением и своим модулем правил без изменения таблиц.

## Защита ставок (7.4)

1. При одобрении модератором создаётся пара ключей RSA-2048 (OAEP, SHA-256). Открытый ключ — в `lots.public_key`, закрытый — только в виде `FakeKms.wrap()`. `unwrap()` отказывает до `closes_at` лота.
2. Сервер проверяет R-03…R-05, R-13, R-18…R-22, сравнивает сумму только с начальной ценой и сразу шифрует `{amount, salt}` открытым ключом лота. Уникальный индекс `(lot_id, user_id)` и уникальный `idempotency_key` гарантируют одну ставку.
3. Контрольный код = `SHA-256(amount + salt + bid_id)` (строки склеиваются без разделителей).
4. Чтобы участник видел свою ставку (R-07) и получил квитанцию письмом (SC-08), сумма дополнительно шифруется **ключом сервера** (`APP_SECRET`, не хранится в базе) — `bids.owner_ciphertext`, а тело письма-квитанции хранится зашифрованным (`notifications.sealed`). Доступ только к базе не раскрывает ни одной суммы.
5. При вскрытии закрытый ключ разворачивается, каждый код проверяется, суммы и соли записываются, закрытый ключ удаляется из лота. Соли публикуются в итоге — любой проверяет код в браузере.
6. Суммы ставок не пишутся в журнал, логи ошибок и админку до итога.

## Отклонения и уточнения PRD

| Место PRD | Решение |
|---|---|
| R-06 против 7.4.4 («для админа есть только число ставок и участников») и 7.1 («WebSocket для … числа участников») | Выбран строгий R-06: до конца **никто**, включая администратора, не видит даже числа ставок. Для решения о снятии лота (R-15) администратору это не нужно — снять можно в любом случае. |
| WebSocket для таймера и итога | Опрос API (на «идёт» — раз в 20 с, во время вскрытия — раз в 2,5 с) + сверка таймера со временем сервера. Ставка сравнивается со временем сервера в момент приёма (SC-10). |
| SC-16 / SC-17: молчат обе стороны | Применяется SC-16 (депозит победителя спорный, мера по лестнице), и продавец дополнительно блокируется на создание лотов до решения администратора. |
| SC-18: мониторинг | Сервер пишет «пульс» в базу; при старте после простоя > 5 мин лоты, у которых конец попал в последний час с простоем, фиксируются как затронутые — их вскрытие ждёт решения администратора («Сбои» в админке). Можно зафиксировать сбой вручную. |
| R-14 «родственники» | Проверка по документу (один документ — один аккаунт) и сигнал S-4 (общее устройство/IP, карта, фамилия, повторные победы у одного продавца) для модератора. |
| AU-04: «если старого номера нет — повторное селфи» | Не реализовано в 0.1: смена номера только с кодами на старый и новый номер. |
| AU-06: капча | Не реализовано: ограничение частоты по IP/номеру/пользователю (в памяти процесса). |
| Q-01 (спорный депозит) | До решения администратора депозит остаётся заблокированным; кнопки «Освободить» / «Списать» с обязательным основанием в журнале. |
| Q-02 (срок блокировки банка) | В фейковом банке 30 дней (`settings.hold_days`), продление за 72 ч — новая блокировка, потом отмена старой. |
| Q-07 (осмотр) | Не реализовано (телефон продавца показывается только после подтверждения сделки обеими сторонами). |
| Годовой доступ: оплата | Только привязанной картой (одностадийная оплата по привязке), статус проверяется у шлюза до активации. |
| Админка | Только на русском (внутренний инструмент автора). |
| Карта на карточке лота | Встроенная карта OpenStreetMap, адрес — до улицы. |

## Режим тестирования (`DEV_TOOLS=true`)

Песочницы банка и KYC, страница `/dev` (все SMS и письма, текущие TOTP, сдвиг времени лота и часов сервера), показ SMS-кодов на экране, приём SVG-фото. В боевом режиме эти маршруты возвращают 404, а часы сервера сдвигать нельзя.

## v0.3 — изменение ставки (PRD v2, решение 9)

- **Было (PRD v1, SC-09):** одна ставка, изменить нельзя.
- **Стало:** одна ставка на участника, до `settings.bid_max_changes` (по умолчанию 3) изменений до конца торгов — повысить или понизить. Endpoint `PUT /api/lots/:id/bids` с подтверждением (step-up) и ключом идемпотентности; повтор с тем же ключом изменение не тратит.
- Строка `bids` всегда хранит текущую версию — вскрытие не менялось. История — в `bid_versions` (миграция 003), суммы там тоже только зашифрованы; в журнал (`bid.changed`) сумма не пишется (R-06, 7.4).
- При равных суммах побеждает тот, чья **последняя** версия пришла раньше по времени сервера.
- Депозит и попытка тарифа при изменении повторно не берутся.

## v0.3 — тарифы по числу участий (PRD v2, решения 4–5)

- **Было (6.5, R-18):** годовой доступ ограничен начальной ценой лота (Базовый ≤ 2 000 000 ֏ / Полный).
- **Стало:** у тарифа `participation_limit` (Standard 10, VIP 50, Premium — без лимита; `NULL` = без лимита). Ограничение по цене (`max_start_price`) осталось в модели и работает вместе с лимитом — так тесты v1 продолжают проверять R-18.
- **«Участвовать» = регистрация на лот = блокировка взноса.** В этот момент списывается 1 попытка (`participation_credits`, тип `spent`). За тот же лот повторно не списывается; по лоту, где пользователь уже участвует, ставка и изменения принимаются даже при 0 попыток.
- **Возврат попытки** (`refunded`): банк отказал в блокировке взноса; лот снят продавцом или администратором; решение модератора (`POST /api/admin/users/:id/participations` с `lotId`). Без `lotId` модератор **начисляет** попытку (`granted`). Причина обязательна, всё — в журнал.
- Пользователь получает **pop-up** — непрочитанное `inapp`-уведомление (`GET /api/me/popups`, закрытие `POST /api/me/popups/:id/read`).
- Ошибка `PARTICIPATIONS_EXHAUSTED`, если доступ есть, но попытки кончились. При повышении тарифа использованные попытки переносятся.
- Демо-данные: тарифы v1 оставлены неактивными, активны Standard / VIP / Premium.

## v0.3 — статусы лота v2, отдельные даты, сортировка каталога (PRD v2, §2 и решение 11)

- Внутренний `lots.status` (v1) не менялся. Для покупателя добавлено поле **`stage`**: `upcoming` (скоро) → `registration_open` → `in_progress` (торги и вскрытие) → `awaiting_contract` (итог есть, договор не подписан; v1 `finished`) → `finished` (продано; v1 `sold`) / `no_sale` → `cancelled` (v1 `withdrawn` / `invalidated`).
- Новые даты лота (миграция 005): `published_at` — показ в каталоге, `registration_opens_at` — открытие «Участвовать», `allow_late_registration` — регистрация во время торгов. Пустые даты = сразу после одобрения (поведение v1). Проверка: показ ≤ регистрация ≤ начало торгов.
- До `published_at` лота нет ни в каталоге, ни по прямой ссылке (кроме продавца). До `registration_opens_at` взнос не принимается (`REGISTRATION_NOT_OPEN`); после старта торгов — только при `allow_late_registration` (`REGISTRATION_CLOSED`).
- Каталог по умолчанию сортируется по PRD v2: торги → регистрация → скоро → ждёт договора → завершён / не состоялся → отменён. Отменённые после публикации лоты теперь видны (внизу). Фильтр `?stage=`.

## v0.3 — взнос 0–10 % задаёт продавец; «Счёт участника» (PRD v2, решение 6, F6)

- **Было (R-13):** депозит 1 % от начальной цены, но не меньше 200 000 и не больше 2 000 000 ֏.
- **Стало:** продавец на шаге «Цена и даты» задаёт `guarantee_percent` 0–10 % (шаг 0,1; по умолчанию `settings.guarantee_default_bp` = 1 %). Взнос = ровно этот процент, без минимума и максимума (`guaranteeFor`). Лоты без процента (созданные до v0.3) считаются по правилу v1.
- **0 %** — регистрация без обращения к банку: запись взноса 0 ֏ со статусом «заблокирован», попытка тарифа списывается как обычно.
- **Не хватает средств:** при отказе банка ответ содержит сумму и карту (`reason: INSUFFICIENT_FUNDS`), сайт показывает окно «Не хватает средств. Пополнить?» — «Да» ведёт к картам, «Нет» закрывает.
- **«Счёт участника»** (`GET /api/me/account`, вкладка в кабинете): заблокировано / возвращается / возвращено / удержано и список взносов. По PRD v2 §7 деньги пока **блокируются на карте** (вариант A); при переходе на эскроу банка изменится источник данных, а не интерфейс. Собственного кошелька с пополнением нет — для него нужна лицензия (§7, вариант C) и решение юриста (§8).
- Демо-данные: за каждый внесённый взнос списана попытка тарифа.

## v0.3 — цепочка мест 1 → 2 → 3 и деление удержанного взноса (PRD v2, решения 7–8, §6)

- **Было (v0.2):** лот переходит только 2-му месту и только в течение `second_chance_days` (5) дней после итога; 3-му — нет.
- **Стало:** после вскрытия взнос держат первые `settings.chain_places` (3) мест, им сразу пишется «вы на N-м месте…». Отказ или молчание 48 ч текущего покупателя → сделка переходит следующему месту по **его** ставке (`deals.round` = номер места), новый срок 48 ч. Нет следующего места с заблокированным взносом → «не состоялся». Взносы мест цепочки освобождаются, когда сделка подтверждена до продажи (`sold`), сорвана продавцом или признана недействительной.
- `second_chance_days` по умолчанию **0 = без окна**. Значение > 0 возвращает режим v0.2 (окно в днях); тест покрывает оба режима.
- **Удержание взноса** отказавшегося: как и раньше, взнос сначала «спорный», решает администратор (Q-01 ждёт юриста). При решении «удержать» создаются две выплаты (`payouts`): продавцу и платформе по `forfeit_platform_bp` (20 %, вариант B из PRD v2 §6), продавцу — письмо. Перевод денег по выплатам — следующий шаг (зависит от модели денег §7).

## v0.3 — вход по email или телефону + пароль (PRD v2, решение 1)

- **Было (AU-01, SC-01):** вход только по телефону и SMS-коду, без пароля.
- **Стало:** `POST /api/auth/register` (email или телефон в одном поле + пароль ≥ 8 символов, буквы и цифры, согласия) → код подтверждения (email — `email_codes`, телефон — `otp_codes` purpose `register`) → `POST /api/auth/register/confirm` подтверждает контакт и сразу открывает сессию; пользователь «не проверен» (`kyc_status = none`). `POST /api/auth/login` — по паролю; до подтверждения контакта — `CONTACT_NOT_CONFIRMED`. Пароль — argon2.
- **Защита от подбора:** 5 неверных паролей подряд → вход закрыт на 15 минут (`login_max_attempts`, `login_lock_min`); для несуществующего аккаунта ответ тот же, без счётчика.
- **«Забыли пароль»:** `POST /api/auth/password/forgot` всегда отвечает одинаково; ссылка на 30 минут, одноразовая, в базе только хэш токена (`password_resets`). `POST /api/auth/password/reset` меняет пароль и завершает **все** сессии.
- **SMS-вход v1 остаётся** (вкладка «По SMS-коду») и теперь отмечает телефон подтверждённым (`phone_verified_at`).
- Зарегистрированному по email **без телефона** подтверждения по SMS (ставка, взнос, сделка) отвечают `PHONE_REQUIRED`; телефон добавляется в профиле одним кодом на новый номер.
- Email уникален без учёта регистра (`users_email_lower`).

## v0.3 — проверка личности: KYC-сервис + решение модератора (PRD v2, решение 2)

- **Было (SC-02):** положительное заключение KYC-сервиса сразу делало пользователя «проверен»; модератор смотрел только сомнительные случаи.
- **Стало (`settings.kyc_require_moderator = true`):** положительное заключение ставит заявку в очередь модератора (`kyc_status = manual`, в `kyc_pending` — ФИО, дата рождения, хэш документа, заключение сервиса, время подачи); пользователю письмо «документы на проверке». Жёсткие правила (младше 18, документ уже использован, R-14) по-прежнему отклоняют сразу, без модератора.
- Очередь: `GET /api/admin/kyc`. Решение: `POST /api/admin/users/:id/kyc` — подтвердить, или отказ / возврат на исправление **только с причиной**; причину видит пользователь в профиле, в журнале — модератор. После отказа можно пройти проверку заново.
- `kyc_require_moderator = false` возвращает поведение v1 (тест покрывает оба режима).
- Собственной загрузки документов на сайте нет: документы и селфи собирает KYC-сервис, у нас — только итог и хэш (AU-07).

## v0.3 — хэш-цепочки журнала и счёта участника (PRD v2, F8 и F11.3)

- **`ledger`** — движения по «Счёту участника». Заполняется **триггерами базы**, поэтому ни одно место в коде не может «забыть» запись: взнос заблокирован / возвращён / удержан, оплата (тариф, комиссия…), попытка тарифа списана / возвращена / начислена. Таблица только на добавление.
- **`hash_chain`** — хэши, тоже только на добавление: `hash = sha256(prev_hash | поля записи)`, первая запись — от 64 нулей. Цепочки: `audit` (весь журнал аудита) и `ledger:<user_id>` (у каждого участника своя — он проверяет свою, не видя чужих).
- `audit_log` по-прежнему нельзя менять, поэтому хэши не дописываются в него, а «запечатываются» фоновой задачей (`ChainService.seal`, каждый такт планировщика и перед проверкой). Порядок цепочки — порядок запечатывания (`seq`), записи поздно закоммиченных транзакций просто попадают в цепочку позже.
- Канонические строки: счёт — `prev|id|user_id|kind|amount|ref|created_at(ISO)`; журнал — `prev|id|actor_id|action|entity|entity_id|JSON(before)|JSON(after)|at(ISO)`.
- **Проверка:** участник — «Счёт участника» → «Проверить хэши», SHA-256 считается в браузере (WebCrypto) по данным `GET /api/me/ledger`.
